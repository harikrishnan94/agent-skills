# Research behind the reduce-complexity skill

This is the research record for the October 2026 rewrite of
[`skills/reduce-complexity/SKILL.md`](../skills/reduce-complexity/SKILL.md).
The rewrite makes the skill establish what a change is for before judging
it, and then look for a way to reach the same intent that is simple,
boring, short and, where the problem allows, elegant. The skill itself
stays one file and cites no sources; this page holds them.

## How it was made

Five topics were researched by reading primary sources:

1. Definitions of simple, elegant, short and boring.
2. How to identify a change's intent, and when to ask.
3. How to search for a simpler approach, and how that search fails,
   especially when an LLM does it.
4. Industry reviewer guides: Google's engineering practices, the Linux
   kernel, LLVM and Chromium.
5. Empirical code review research: Pascarella et al. 2018, Bacchelli and
   Bird 2013, Sadowski et al. 2018, Bosu et al. 2015, and Turzo and Bosu
   2023.

The first three topics were then fact-checked claim by claim against the
cited source: 49 of 60 claims held as written and 11 needed a correction.
None were wrong. The tables below show the corrected wording. For topics 4
and 5, a script checked that every quoted passage appears word for word in
the fetched source. No rule in the skill depends on a detail the fact-check
corrected.

## Where each rule comes from

| Skill rule | Sources |
|---|---|
| **Simple**: fewer braided concerns, less new state, fewer obligations on callers | Hickey, "Simple Made Easy" (simple means not braided; easy means familiar); Ousterhout's debate with Martin (entangled methods: understanding one means reading the other); Moseley and Marks, "Out of the Tar Pit" (state and control as the main causes); Google's reviewer guide (too complex: not understood quickly, or callers likely to introduce bugs) |
| **Boring**: the lowest rung that does the job, with prevalence and failure-mode receipts | McKinley, "Choose Boring Technology" (known failure modes; ask how you would solve it without adding anything new); Google's Go style guide ("least mechanism": core language, then standard library, then an existing core library, then something new) |
| **Short**: fewest elements a reader must learn, never characters or lines | Beck's rules of simple design via Fowler (fewest elements, ranked last); Dijkstra, EWD340 (counting symbols is conceptually irrelevant); Pike (length is not a virtue in a name); the Zen of Python (sparse is better than dense) |
| **Elegant**: a restatement under which a special case or error path disappears | Dijkstra, EWD1284 and EWD896 ("ingeniously simple and effective"); Torvalds' "good taste" linked-list example; Ousterhout's "define errors out of existence"; Hoare's Turing lecture ("so simple that there are obviously no deficiencies") |
| Tie-break order: intent met, then simple, boring, short | Beck's first rule (passes the tests); the Go style guide's ranking (clarity, simplicity, concision, then consistency as a tie-breaker); Kernighan and Dijkstra against clever code |
| Familiarity is not evidence; prevalence is | Hickey's "easy is relative to the person"; McKinley's organisation-level view of boring |
| Intent first, with a source order and an intent record | Google, "Navigating a CL in review" and "What to look for" (does the change make sense; does it do what the developer intended); Bacchelli and Bird (understanding the reason for a change is the hardest part of review); Al Safwan and Servant (the goal is the most important part of a commit's rationale); SWE-bench's fail-to-pass and pass-to-pass tests; Google design docs (non-goals) |
| Ask with concrete behavior examples, after reading; state assumptions when unattended | The underspecified SWE-bench study (models rarely ask unless prompted; behavior questions help most); TiCoder (clarifying intent through test examples) |
| Sketch the boring solution before reading the diff closely | Code-model anchoring studies (code placed in the prompt is copied into outputs); requirements fixation in design studies; Ousterhout's "design it twice"; Sphinx (derive a pseudo-solution from the stated intent, then compare) |
| Evaluative words in PR text feed nothing | The framing-attack study, where calling a change "safe" or "improved" in PR text collapsed LLM vulnerability detection |
| An approach finding needs an executed prototype and compared inputs | LLMs misjudging semantic equivalence; the SWE-bench study where 29.6% of test-passing patches behave differently from the developer's patch; fix-guided verification filters; Liu et al. on unsafe LLM refactorings |
| Keep every line the move does not require | Zhu, Lim and Kan on over-editing (a preservation instruction cuts excess edits) |
| "Equally valid" alternatives are dropped; the author decides | Google, "The standard of code review" |
| The approach finding comes first in the report | Google, "Navigating a CL in review" (send major design comments first) |
| One logical change; report a split instead of simplifying across intents | Linux kernel, "Submitting patches"; LLVM's developer policy |
| Over-engineering means more generic than needed | Google, "What to look for"; the kernel's coding guide (abstraction only to the level required); Chromium's CL tips |
| The **Unless** line in an approach finding | Chromium's review-respect guidance (a "bad" change usually means one side has information the other lacks); Google's pushback guidance |
| Imperative titles, neutral tone, no praise, caps, no re-raising declined findings | Bosu et al. 2015 (usefulness of comments at Microsoft); Turzo and Bosu 2023; Sadowski et al. 2018 (analyzers with high "not useful" rates lose trust) |
| Enumerate callers before proposing an alternative | Bosu et al. 2015 (first-time reviewers of a file write useful comments about half as often) |

## What the skill did not adopt, and why

- **Sources inside the skill.** The skill stays one file with no references
  directory, so the sources live here.
- **Always sketching a second, radically different design.** The skill
  sketches one only when no listed move fits, to bound run cost.
- **Google's "new complexity must be cleaned up before submission".** Every
  finding stays non-blocking and an approach finding may be a follow-up,
  because the author decides; the skill reports the evidence.
- **Lines of code as a benefit.** The definitions research rules it out. A
  smaller diff may appear under switching cost, never as the reason for a
  verdict, although the empirical research treats diff size as a real
  review cost.
- **Dropping question phrasing.** Bosu et al. found question wording
  predicts less useful comments, while Turzo and Bosu rated questions
  fairly high. The skill keeps questions for demoted findings, always in a
  conditional form ("if X holds, delete Y?"), because an unattended run
  cannot settle them.
- **The change-amplification probe** (name the likeliest next change and
  count its edit sites under both shapes). Change amplification stays an
  Impact term; the probe was left out to keep the ledger short.

## What the evaluation added

The eval suite lives outside the repository, so its main lesson is
recorded here. Both the old and the rewritten skill found every planted
simplification and avoided every trap, so graded assertions could not
tell them apart. Blind side-by-side judging could. A first rewrite that
printed its own procedure in the report (the design sketch, a count table
in the skill's vocabulary, step numbers) lost 17 of 21 comparisons with the
old skill, although it stated intent better in all 21. The same analysis
with only its results on the page, in plain words, won 12 of 13. That is
why the skill's report section forbids the skill's own vocabulary and
procedure narration.

## Definitions of simple, elegant, short and boring

| 1 | Hickey separates two words. 'Simple' comes from simplex (one fold): nothing is braided together. 'Easy' comes from 'lie near': near at hand, familiar, or within your current ability. He calls simplicity objective, because you can check whether things are interleaved, and easiness relative ('easy for whom?'). 'Complect' means to braid concerns together. He names constructs that braid concerns: state (value with time), objects (state, identity and value), conditionals scattered through code (versus rules), imperative loops (versus set functions), and actors (versus queues). He also says simplicity can mean more separate components, not fewer, and that tests and type checkers are guardrails, not a source of simplicity. | [Rich Hickey, Simple Made Easy (Strange Loop 2011), transcript](https://github.com/matthiasn/talk-transcripts/blob/master/Hickey_Rich/SimpleMadeEasy.md) | verified |
| 2 | In his written debate with Robert Martin, Ousterhout defines complexity as whatever makes a system hard to understand and modify. A deep method provides a lot of functionality behind a simple interface. A shallow interface does not reduce much of what the programmer needs to know; at the limit the caller must understand the whole implementation. He calls methods 'entangled' when understanding one internally means reading the other, and gives the symptom: flipping back and forth between the implementations of two methods. He rejects arbitrary numeric method-length limits (such as 2-4 lines) because they push code into shallow, entangled pieces. In his TDD section he advises asking repeatedly: knowing everything I know now, would I have chosen the current structure for the code? | [John Ousterhout and Robert Martin, A Philosophy of Software Design vs Clean Code (discussion README)](https://github.com/johnousterhout/aposd-vs-clean-code/blob/main/README.md) | corrected (claim shown corrected) |
| 3 | Notes on the book list three symptoms of complexity: a seemingly simple change needs edits in many places; cognitive load (how much a developer must know); and unknown unknowns, which the notes call the worst of the three. The notes name two causes: dependencies and obscurity. Red flags include shallow modules, information leakage (the same knowledge used in several places) and pass-through methods; the notes also warn against pass-through variables, splitting methods too finely, and special cases. They say a simple interface matters more than a simple implementation, that an approach with more lines of code is sometimes simpler, and that you should design it twice. They advise designing the normal case so it handles edge conditions without extra code (the notes do not use the phrase 'define errors out of existence' or cite a chapter). | [Derek Sivers, notes on A Philosophy of Software Design (secondary summary of Ousterhout's book; the book itself was not read in this run)](https://sive.rs/book/PoSD) | corrected (claim shown corrected) |
| 4 | Brooks divides software work into essence (designing the conceptual structures) and accidents (representing them in a language and mapping them to the machine). The essence has four properties: complexity, conformity, changeability and invisibility. Conformity is complexity forced by other systems' interfaces, which no redesign of the software alone can remove. He names buy-versus-build as the most radical attack on the essence: not constructing the software at all. | [Frederick P. | 5 | Moseley and Marks define essential complexity as complexity inherent in the problem as the users see it. Accidental complexity is everything else, including complexity caused by performance needs and by imperfect languages or infrastructure. They name state and control as the main causes, with code volume largely a side effect of those two: it is the easiest form of complexity to measure and it makes the other causes worse. Their state table treats derived data as accidental state; mutable derived data counts as derived only when its derivation has an inverse, and otherwise it is really input. Their strategy is to avoid accidental complexity where possible and to separate it where not. They argue that informal reasoning matters more than testing, because better reasoning means fewer errors are made, while better testing only finds more. | [Ben Moseley and Peter Marks, Out of the Tar Pit (2006)](https://curtclifton.net/papers/MoseleyMarks06a.pdf) | verified |
| 6 | Fowler lists Beck's rules of simple design in priority order: passes the tests, reveals intention, no duplication, fewest elements. He calls the order of rules two and three unimportant because they refine each other. He adds that elements added for future flexibility usually made systems harder to modify. Beck himself, quoted in a footnote, says that in the rare conflicts (tests are the only examples he recalls) empathy wins over a strictly technical metric. | [Martin Fowler, BeckDesignRules (bliki)](https://martinfowler.com/bliki/BeckDesignRules.html) | corrected (claim shown corrected) |
| 7 | Linus Torvalds' 'good taste' example, as the README explains it, compares two ways of removing an item from a singly linked list. One treats the head of the list as a special case with an if. The other uses a pointer to a pointer, so the head is handled like any other link. His stated point is that rewriting the problem can make a special case go away and become the normal case. The README's author concedes that the elegant version is not immediately evident without explanation, and leaves open whether it really shows good taste. The TED transcript itself was not available in this run. | [mkirchner, linked-list-good-taste (README explaining Torvalds' TED 2016 example; secondary source)](https://github.com/mkirchner/linked-list-good-taste) | verified |
| 8 | In 'Notes on Programming in C', Pike gives these rules. You cannot tell where a program spends its time, so measure before adding speed hacks. Fancy algorithms are slow when n is small, and n is usually small. Fancy algorithms are also buggier and harder to implement. Data dominates: with the right data structures, the algorithms become self-evident. Under 'programming with data', he says logic made of many independent details is often better written as a table than as many if statements. On names, he writes 'Length is not a virtue in a name; clarity of expression is.' He prefers names with the least length and the most information, letting context fill in the rest. | [Rob Pike, Notes on Programming in C (1989), section 'Complexity' and 'Variable names'](http://doc.cat-v.org/bell_labs/pikestyle) | verified |
| 9 | Pike's Go proverbs include: clear is better than clever; a little copying is better than a little dependency; reflection is never clear; the bigger the interface, the weaker the abstraction; interface{} says nothing; and gofmt's style is no one's favorite, yet gofmt is everyone's favorite. | [Rob Pike, Go Proverbs (Gopherfest 2015)](https://go-proverbs.github.io/) | corrected (claim shown corrected) |
| 10 | Google's Go style guide ranks its principles: clarity, then simplicity, then concision, then maintainability, then consistency. | 14 | In his Turing lecture, Hoare describes two ways to build a software design: make it so simple that there are obviously no deficiencies, or so complicated that there are no obvious deficiencies.
